# First application binding: opt-in passive evidence backup

24 October 2026. The source assembler now accepts `--progress-backup-runtime` and binds the existing coordinator to the real immutable 100380 main/preferences code. The separate Dart define `DEDA_STABILITY_PROGRESS_BACKUP_PILOT` defaults to false. Assembly alone never enables it, and existing official build/signing workflows and archive remain unchanged. No production rules have been deployed. Do not enable this against production before reviewing/deploying compatible rules with the owner's approval.

## Bound execution

The application root wraps DedaApp with DedaProgressBackupHost, outside the route tree. Both ordinary and instrumented startup paths receive the same wrapper. It survives navigation/language changes. A single controller lazily creates one Firebase observer/driver/coordinator for that root when the pilot is enabled and Firebase exists. It observes SDK identity and uses the owner IO only for principal/install observation; it never calls sign-in, sign-out, trusted-session restoration, role checks that mutate auth or wallet methods.

DedaPreferences.load/saveLogin/logout each invalidate the account intent BEFORE their first await. Load and successful save complete the canonical numeric account after local initialization/persistence; logout leaves it absent. An older operation cannot complete a newer selection token. Runtime guards also compare current local account, account epoch, SDK UID/kind/revision, root lifetime and lifecycle epoch. Returning A→B→A cannot revive first-A work. Existing preference/auth writes are preserved; these hooks protect backup dispatch, not all original auth races.

One bounded attempt runs at first frame, completed selection or app resume. Pause/hidden/detached invalidates it. Admin/non-anonymous/missing sessions cannot dispatch. The archive independently requires matching server session/install/users proof before preparation/upload. Busy events are dropped, never queued/retried automatically; if a selection/resume happens during an older request, a later resume is needed. The coordinator's native transport lane remains busy even after its UI timeout, until its original Future settles. No network retry timer or boot/login wait is introduced.

Pending journals retain priority. The driver uses a secure 24-byte random capture ID and resolves the exact pending intent before another capture. After verified readback and journal retirement it remembers only the last account/exact acknowledged capture in process memory. Later unchanged local text is skipped only after fresh owner proof; this cache gives no role/balance authority. A restart may capture identical text once more with a new ID, without applying any reward. There is no cross-process dedupe guarantee. Device-global favorites/places/drafts are excluded.

The data remains untrusted raw evidence. No balance or purchase ownership is restored/merged, no source key is deleted, and no atomicity of the three independent financial writers is claimed. The old-UID/missing-server pending case remains blocked and retained. Actual app activation, coordinated auth integration, trusted financial migration, nonfinancial backup and two-phone acceptance remain pending.
