## أين يوجد الربط فعلياً

- قراءة الهوية ودورة حياتها فقط مربوطتان في DedaQa32ActiveAccountScope خلف DEDA_STABILITY_IDENTITY_PILOT الافتراضي false. القياس خلف DEDA_STABILITY_STARTUP_METRICS الافتراضي false.
- أضيف تنظيم مداخل المصادقة الأصلية وحفظ الهوية/مطابقة admin_entry_access وself-heal والخروج/تغيير كلمة المرور في المصدر الناتج عند --auth-runtime، خلف علم معطل افتراضياً؛ راجع AUTH-SESSION-RUNTIME. لا تخلط هذا الربط الجديد مع محولي المالك والإدارة المنفصلين. قبول PIN المربوط مع SDK Android نجح بـ13 حالة؛ واجهة ديدا الكاملة ومسارات Backend/Admin native ومعالجة حالات الانتهاء الجزئي لا تزال مطلوبة قبل التفعيل.
- أضيف ربط DedaProgressBackupCoordinator من root وload/saveLogin/logout في مصدر 100380 المستعاد عند --progress-backup-runtime، خلف DEDA_STABILITY_PROGRESS_BACKUP_PILOT الافتراضي false. هو ربط سلبي لا يغيّر auth؛ تشغيل الحفظ للمستخدمين لم يُفعّل. busy trigger يسقط وينتظر حدث رجوع تالياً، ولا طابور/إعادة تلقائية. لا استعادة رصيد أو بيانات عامة للجهاز.
- لا Source.server أو sessionPresent أو bool signIn أو كاش يمنح دوراً أو ملكية. قواعد الخادم وإثبات الحساب يظلان المرجع.
- مرشح القواعد أضيف إليه users self-get المطلوب للنقل. قواعد المستودع الأصلية تسمح به بالفعل؛ قُرئت القواعد المنشورة لاحقاً قراءة فقط واختُبرت النسخة الإضافية بـ93 حالة ولم تنشر. لا تستبدل قواعد التطبيق بمرشح الأرشيف، ولا تجعل users/profile كتابات readonly في الدمج لأنها مطلوبة في التطبيق الأصلي.
- نموذج المصالحة/الترحيل تحت tools/app_stability/progress_archive فقط، بلا functions/index.js أو API أو تفعيل. حماية receipt doc لا تعني إنتاج دليل مصدر صحيح.
