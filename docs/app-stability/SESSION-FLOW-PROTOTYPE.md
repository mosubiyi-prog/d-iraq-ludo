# نموذج تسلسل انتقالات الجلسات — غير مربوط بـFirebase

## نطاق الدفعة

`DedaSessionFlowPrototype` نموذج Dart مستقل يمرر كامل سلسلة الدخول أو الاستعادة خلال `DedaSessionTransitionGate` واحد مشترك. `DedaSessionFlowPort` عقد للمحول؛ المنفذ الوحيد حالياً مزيف داخل الاختبار. لا استيراد في main أو PinAuth أو Backend، ولا تفعيل للمصادقة أو إنشاء نسخة APK. `--session-flow` يضيف النموذج والأساس إلى مصدر الفحص فقط.

مصدر الدفعة النهائي: `4754c0c3fb1b84f3e6f71cbb38944d1086413aa0`.

| المسار | التسلسل المختبر |
| --- | --- |
| دخول المالك | تجهيز جلسة مجهولة ← إثبات PIN ← كتابة الجلسة ← قراءة إثبات المالك ← قراءة الملف ← وثوق الجهاز ← إسقاط users ← حفظ الحساب المعروف محلياً |
| استعادة المالك | جلسة مجهولة ← كتابة جلسة التثبيت الموثوق ← إثبات المالك والتثبيت؛ دون PIN أو تعديل الملف أو إضافة وثوق جديد |
| دخول الإدارة | SDK ← إثبات المدير الفعّال ودوره ← تحديث الملف ← إشعارات ثانوية ← سجل التدقيق |
| رفض مدير غير فعال | إنهاء جلسة المدير المرفوض فقط إن بقيت هي الجلسة الحالية؛ لا إنهاء جلسة أحدث |

## الحواجز التي يختبرها النموذج

- انتقال واحد حي للمالك والإدارة معاً. كل استدعاء نية مستقلة؛ الضغط المتكرر يرفض busy دون دمج PIN أو كلمة مرور أو الاحتفاظ بهما في مفتاح.
- المساعدات ترث permit نفسه، ولا تدخل gate ثانياً. بعد أي انتظار تجهيز محلي يتحقق المحول من permit **ومن UID ونوع الجلسة ورقم جيلها** قبل إرسال الكتابة التالية. لهذا يستقبل حفظ الحساب المعروف كائن المستخدم أيضاً.
- رقم جيل SDK مستقل عن جيل النية؛ انتقال A→B→A لا يحيي نتيجة قديمة. لا يبطل المحول النية لمجرد إشعار الدخول المتوقع من العملية نفسها.
- انتهاء مهلة الواجهة يحجز المسار حتى انتهاء Future الأصلية، ويمنع الخطوات التالية والنشر المتأخر؛ لا يلغي أثراً أُرسل بالفعل إلى SDK أو Firestore، ولا يطلق إعادة أو rollback آلياً.
- استعادة القسم النشط لا تنهي جلسة إدارة. الأصل background يرفض كل الانتقالات الثلاثة. SDK وحده لا يثبت المالك أو الإدارة.
- فشل الإشعارات ثانوي، لكن انتهاء المهلة أو تبدل المستخدم خلالها يمنع التدقيق والنجاح المتأخر. فشل التدقيق لا يعيد تسجيل الدخول ولا ينهي المدير تلقائياً.

## قبل محول Firebase حقيقي

قراءة إثبات المالك بعد كتابة الجلسة **عقد مقترح إضافي في النموذج**؛ ليست وصفاً بأن المصدر الأصلي ينفذ هذه القراءة حالياً أو أن مخططه يحتوي هذه الحقول حرفياً. يلزم تحديد قراءة خادم يمكن للقواعد الحالية إثباتها وتعيينها إلى النوع دون قبول cache أو علم محلي كصلاحية. نوع Profile هنا بيانات عرض محدودة، وليس مخطط profile/users كاملاً أو تصريحاً لنسخ أرصدة أو ملكية.

يجب مطابقة مصدر 100380 المستعاد والقواعد الحالية، بما فيها installId، وصيغ profile/users، وحفظ الهاتف المعروف، وdisplayName الاختياري وسياسة أخطائه. لا تغيّر القواعد أو مخطط البيانات أو سياسة فشل التطبيق لتناسب المحاكاة. راجع `SESSION-BOUNDARIES.md` وJSON المرافق؛ دعوات الإدارة وتغيير بيانات الدخول والخروج وتنظيفه الجانبي ما زالت تحتاج تسلسلات مستقلة متناسقة قبل أي حماية عامة.

توفير signOutIfCurrent لا يجعل Firebase signOut قابلاً للإلغاء أو مشروطاً ذرياً: افحص المستخدم قبل الإرسال، وسجّل تغيرات SDK، وأبق القفل حتى انتهاء العملية. أثر أرسل قبل تبديل خارجي قد يكتمل؛ لا يدعي النموذج القدرة على التراجع عنه. يجب أن تستخدم المسارات المحمية gate المشترك، وأن يفحص الربط سلوك SDK الحقيقي خارج هذه المحاكاة.

## الفحوص وحدود الاستنتاج

المجموعة تتضمن 36 حالة: تسلسل المالك والإدارة، ربط الإثبات بالحساب، PIN خاطئ، تثبيت غير موثوق، مهلة SDK وخروج صريح، انتهاء تجهيز محلي، تبدل الحساب أثناء تجهيز الوثوق والحفظ المحلي، تغير النية وA→B→A، التنافس والضغط المتكرر، رفض الإدارة، والإشعارات والتدقيق المتأخران.

نجاح هذه الحالات يثبت العقد بالمحول المزيف فقط؛ لا يثبت أذونات خادم أو أمان بيانات إنتاج أو تحسن سرعة هاتف. فحص الاستعادة يثبت أن الخيار يضيف ملفين فقط ويحفظ main/PinAuth/Backend بالبايت ولا يضيف Android. المرجع وتجربة الهوية والقياس تبقى ضمن مصفوفة QA نفسها. نتائج التشغيل المعتمدة في `CURRENT.md` و`RESULTS-2026-10-23.md`.
