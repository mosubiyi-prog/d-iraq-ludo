# جاهزية الجلسات وحدود ربط منظم الانتقالات

نقطة الرجوع قبل هذه الدفعة: `5e6e7b5a3cde601508da40b9a44b57b273bc6d2b`.

هذه مراجعة مصدر وبناء أساس واختباره قبل الربط. **لم تُربط المصادقة الحقيقية بالمنظم بعد**، ولا تصح نسبة الحماية الجديدة إلى سلوك النسخة المنشورة. `--session-gate` ينسخ module غير مربوط لتشغيل الفحوص فقط؛ لا ينشئ حسابًا ولا يغير تسجيل الدخول.

## المصدر الذي روجع

المصدر هو ملفات اللقطة الثابتة 100380 ذات manifest، وليس ملفات backend وmain القديمة في جذر المستودع. إحداثيات 13 موضع SDK مباشر روجعت داخل `deda_backend.dart` و`deda_pin_auth.dart` وبصمتا الملفين في `SESSION-BOUNDARIES.json`. هذا ليس جرد استدعاءات كاملاً لكل التطبيق أو إثبات تغطية تشغيلية؛ توجد استدعاءات أعلى مستوى وعمليات Firestore وآثار خلفية تحتاج حدودًا أوسع من موضع SDK وحده.

## لماذا لا يكفي قفل signIn منفردًا

| --- | --- | --- |
| `DedaBackend._ensurePublicUser` | يعيد أي جلسة SDK موجودة؛ ينشئ مجهولة إذا غابت | وجود User ليس إثبات مالك أو مدير؛ لا يستبدل جلسة موجودة لمجرد جاهزية قسم |
| `DedaPinAuth._ensureAnonymousSession` | ينهي غير المجهولة، ثم signIn مجهول بمهلة انتظار 12 ثانية | لا يستدعى تلقائياً من الخلفية؛ انتهاء مهلة الواجهة لا يحرر طلب SDK الحي ولا يجيز محاولة متداخلة |
| `DedaPinAuth.signIn` | يكتب محاولة PIN ثم deda_sessions ثم profile/users وقائمة الجهاز الموثوق | تغطية السلسلة المنطقية كاملة، وحراسة النية والـUID المثبت قبل الكتابات التالية وبعد الانتظار |
| `DedaPinAuth.createAccount` | ينشئ بيانات اعتماد ودليلًا وملفًا بمعاملات وكتابات حساب | انتقال صريح واحد، وإبقاء المعاملات وقواعد الخادم؛ لا تكرار تلقائي بعد نتيجة غير مؤكدة |
| `restoreTrustedSessionForAccountKey` | يكتب deda_sessions مع installId؛ قواعد الخادم تثبت الثقة | يُعامل كتغيير جلسة لا كقراءة؛ لا اعتبار prefs أو معرفة accountKey سلطة، ولا استعادة خلفية تطرد الإدارة |
| `_ensureOwnerSessionForAccountKey` | قد يستدعي signOutAdmin قبل استعادة المالك | فحص المالك الحالي دون إنهاء جلسته أولاً؛ انتقال خارج جلسة محمية يتطلب فعل مستخدم واضح، لا حدث resume عام |
| `signInAdmin` | دخول SDK، فحص حالة ودور الخادم، تحديث admin وFCM/audit، وخروج عند الرفض | القفل يشمل إثبات المدير وقرار الرفض والخروج التابع له؛ تحريره بعد signIn وحده يسمح بأن ينهي رفض قديم جلسة أحدث |
| `activateAdminInvitation` | إنشاء مستخدم، مطالبة دعوة وكتابة مدير، مع حذف المستخدم/خروج عند فشل جزئي | حدود تشمل كامل التفعيل والتصالح مع النتيجة؛ لا إعادة تلقائية أو rollback عام على جلسة جديدة |
| `changeCurrentAdminPassword` | تغيير اعتماد حساس لمستخدم Firebase | فعل صريح وإثبات الصلاحية الحالي؛ لا استعمال تنظيم الجاهزية بديلاً عن التحقق الأمني |
| `signOutAdmin` و`signOutFirebase` | إنهاء SDK؛ الثاني له تنظيف Firestore خلفي مربوط بـUID ملتقط | إبطال نية الواجهة فورًا؛ فصل خروج SDK عن التنظيف دون اعتباره حماية مكتملة، وفحص التنظيف المتأخر قبل التعميم |
| `DedaPreferences.signOut` | يمسح حالة الحساب المحلية ثم يستدعي خروج Firebase | تنسيق جيل نية الحساب المحلي مع gate؛ لا إحياء حالة حساب سابق من قراءة متأخرة |
| `DedaSocialService.ensurePersonalSession` | يجهز هوية مشاركة ثم يكتب ملفًا اجتماعيًا | ليس فحص جاهزية للقراءة فقط؛ لا تمريره إلى إعادة محاولة منسق القراءات |

## الأساس المنفذ

`DedaSessionReadinessPolicy.inspect` يصف الاحتياج فقط. عدم جاهزية Firebase يمنع استنتاج جاهزية جلسة. وجود SDK user يسمح بوصف sessionPresent للبيانات العامة، لكنه لا يمنح ملكية حساب أو دور إدارة. قراءة مالك قائمة، حتى مع جلسة غير مجهولة، تتطلب إثبات المالك من الخادم؛ لا تفترض السياسة أن المدير لا يمكن أن يكون مالكًا أيضًا. الجلسة غير المجهولة تتطلب إثبات إدارة من الخادم، ولا تُعد مديرًا تلقائيًا.

`DedaSessionTransitionGate` يقبل عملاً واحدًا حيًا. طلب متطابق في الجيل والنوع والأصل ونوع النتيجة يستطيع الانضمام إلى العمل الجاري؛ لا تُخزن النتيجة المكتملة. طلب مختلف يرفض busy ولا يدخل طابورًا ينفذ تسجيل دخول أو خروج لاحقًا دون مراجعة الحالة. لا توجد محاولة تلقائية لأي خطأ.

أصل background لا يجيز أي تغيير جلسة. أصل activeSection يسمح بتجهيز مجهول عند غياب الجلسة أو استعادة مالك على جلسة مجهولة، مع بقاء إثباتات الخادم واجبة داخل العمل. لا يسمح باستبدال جلسة غير مجهولة أو دخول إدارة أو تغيير اعتماد. أصل userAction يعني أن الربط تحقق فعلاً من فعل المستخدم؛ مجرد وضع هذا الوسم على استعادة خلفية لا يحقق الشرط، وليس بديلاً عن صلاحيات الخادم.

الانتظار الافتراضي 12 ثانية. انتهاؤه ينهي انتظار المستدعي ويترك الحجز إلى أن ينتهي Future الحقيقي للعمل. لا تُرسل عملية ثانية وراء SDK ما زال حياً، ولا يؤكد نجاح متأخر لواجهة انتهى طلبها. هذا لا يلغي أو يعكس أثر SDK أو كتابة أُرسلت بالفعل؛ تُراجع النتيجة قبل محاولة جديدة، ولا تنفذ signOut تصحيحيًا قد ينهي جلسة صالحة.

## عقد الاستخدام عند الربط اللاحق

1. استخدم instance مشتركًا لمسار المصادقة كله. instances منفصلة لا تنظم بعضها، ولا تغلف primitive فقط بينما تتم الكتابات اللاحقة خارج الحجز.
2. المفتاح يميز نية الحساب والعملية برمز نية مبهم، دون وضع PIN أو كلمة المرور نفسها فيه. لا تخلط محاولتين بمدخلات اعتماد مختلفة تحت رمز نية واحد؛ أنشئ رمزاً جديداً عند تعديل المدخلات، ولا تنشر المفاتيح في التشخيص.
3. `isCurrent` يحرس **نية المستخدم** وحياة القسم ونسخة الاختيار. لا تقارنه عميانياً بـUID ما قبل الدخول، لأن الدخول المصرح ينتج UID متوقعًا جديدًا. قراءات الهوية تظل لها أجيال SDK مستقلة تُبطل عند تغيره.
4. إبطال الاختيار A→B→A يرفع الجيل حتى لو عاد المفتاح إلى A. أبطل النية عند الخروج أو تبديل الحساب أو إلغاء القسم. العملية الحية تبقى محجوزة حتى تنتهي فعلياً.
5. مرر `DedaSessionTransitionPermit` إلى المساعدات الداخلية، وافحصه قبل كل نداء/كتابة لاحقة وبعد انتظارها وقبل نشر النتيجة. تحقق من UID وaccountKey اللذين أثبتهما الخادم عند حدود الكتابة. الفحص لا يلغي طلباً أُرسل قبل تغير النية.
6. لا تستدعِ gate مجدداً داخل عمله حتى بنفس المفتاح: ذلك قد ينتظر Future نفسه أو يقطع السلسلة. المنظم يرفض الدخول المتداخل في Zone العمل بخطأ محدد؛ المساعدات تستخدم permit الموجود.
7. بعد busy أو timeout أو نتيجة غير مؤكدة لا تُدخل حلقة محاولات. اقرأ حالة SDK/الخادم وراجع نية القسم أولاً؛ أي محاولة انتقال جديدة تبقى ضمن سياسة الفعل الواضح وإثبات الخادم.

التشخيص عدادات ثابتة في الذاكرة فقط، بلا مفتاح أو UID أو هاتف أو اعتماد أو نص خطأ، وبلا طباعة/إرسال. وجود هذا module لا يغير حماية التطبيق الفعلية قبل ربط المسارات المذكورة واختبارها.

## ترتيب أول ربط مستقبلي

ابدأ بمحول مصادقة مزيف على مستوى سلسلة الدخول/الاستعادة الكاملة، يتضمن تغير SDK ورفض إثبات المالك وكتابات profile المتأخرة ومسار دخول الإدارة المقابل. حافظ على بقاء النظير الحقيقي خارج الربط إلى أن يكتمل حصر نقطة كل كتابة وrollback. بعدها اربط مجموعة متناسقة من المسارات خلف تجربة منفصلة؛ لا تعمم gate بين PinAuth وBackend جزئيًا وتعلن المصادقة كلها محمية.


## تقدم اختبار التسلسل الأعلى

نموذج دخول المالك واستعادته ودخول الإدارة نجح في 36/36 حالة بمحول مزيف، دون ربط هذه المواضع الفعلية. راجع `SESSION-FLOW-PROTOTYPE.md` للعقد وحدود readback المقترح وحراسة UID/جيل المستخدم داخل المساعدات. جرد 13 موضعاً لا يعني اكتمال الحماية؛ الدعوات وبيانات الدخول والخروج ما زالت تحتاج تسلسلاتها، ثم ربطاً متناسقاً واختبارات SDK والخادم.


## تقدم محول المالك

أضيف محول Firebase غير مربوط مع 35/35 حالة بمضاعفات النقل والتفضيلات، ومراقب جيل SDK. المصدر الحقيقي في جرد الـ13 موضعاً لم يتغير. التوافق مع PIN/profile/users والقواعد المحفوظة وحدود readback في `OWNER-FIREBASE-PORT.md`. محول الإدارة والمسارات الأخرى ما زالت تحتاج تغطية؛ لا تفعّل owner وحده مع SDK منافس من المسارات الأصلية.


## تقدم محول الإدارة وحدود شاشة الدخول

محول Backend غير المفعّل نجح في 43/43 محاكاة. bool الدخول وFCM/audit والكاش وسياسة status محفوظة، ولا تخويل جديد. شاشة admin_pages تحتوي بعده حفظ الهوية ومطابقة هاتف admin_entry_access وخروج الرفض وربما تغيير كلمة مرور؛ لا تزال تحتاج حراسة منسقة. signInWithPermit يهيئ التركيب دون إعادة دخول gate، وليس دليلاً على ربط الشاشة. دعوات التفعيل أيضاً تتبعها مطابقة وخروج محتمل. التفاصيل في ADMIN-FIREBASE-ADAPTER.
