# DEDA — مرحلة 3: نموذج ناشر المهام اليومية الموثوق (غير منشور)

## المرجع والحماية
- المرحلة 2 المجتازة: `backup-admin-daily-slots-stage2-preview-qa-2026-10-09`.
- نسخة الملاحة المعتمدة: `backup-deda-100319-user-accepted-2026-10-08` بلا تعديل.
- فرع المرحلة 3: `admin-daily-slots-stage3-publisher-2026-10-09`.
- هذا النموذج **ليس منشورًا في Firebase**، ولا يعمل تلقائيًا في الإنتاج، ولا يوجد استدعاء له داخل `functions/index.js`، ولا يغير شاشة المستخدم المثبتة.

## وظائف النموذج
- `functions/deda_daily_task_publisher.js` يحتوي `publishDueDailySlots(db, trustedNow)` لإجراء عمليات Firestore خادمية ذرية.
- يقرأ سجلات `admin_daily_schedule_previews` الخاصة بالبطاقات الثمانية، ويرفض تسجيل الدخول خارج نطاق استبدال البطاقات.
- فقط أثناء أول 15 دقيقة بعد منتصف الليل حسب بغداد، وعندما يساوي حقل `effectiveAt` بالضبط منتصف الليل، يكتب إعدادًا عامّ القراءة للمستخدم المسجل في `deda_daily_published_task_slots`.
- لا يتعامل مع `admin_task_drafts` القديمة، ولا ينشر شيئًا من مسودة لم تُجدول.
- `deda_daily_task_publication_history` يسجل بصورة خاصة الإصدار الجديد وإعداد المهمة السابق، من أجل تطوير الاستعادة المجدولة لاحقًا.
- منع تكرار نشر نفس البطاقة في اليوم نفسه حتى لو اشتغل الناشر مرتين أو بتزامن.
- `rewardsEnabled: false` ثابتة، ولا توجد أي كتابة إلى محافظ النقاط/العملات/الألماس أو أرصدة الإدارة.
- وظيفة اختيار `visit_telegram` تدقق الرابط؛ فتحه لا يثبت الاشتراك ولا يفعل المكافأة.
- وثائق النشر لا يمكن للمستخدم إنشاؤها أو تعديلها: Firestore Rules تمنح للمستخدم المسجل القراءة فقط، بينما السجل التاريخي ومعاينات الإدارة غير عامة.

## اختبار القبول
- GitHub Actions workflow `.github/workflows/qa-deda-daily-publisher-stage3.yml` يشغّل Node Firebase Admin داخل محاكي Firestore المحلي باستخدام مشروع `demo-*` دون صلاحية دخول مشروع الإنتاج.
- الاختبارات تشمل: توقيت بغداد، بطاقة واحدة وباقي 7 سليمة، التشغيل المتكرر والمتزامن، إلغاء المسودة، الفشل خارج منتصف الليل، رفض البيانات الخاطئة/الروابط المضللة، حفظ إعداد سابق، منع مستخدم من الكتابة، عزل السجل الإداري، ونشر تغييرين منفصلين.
- **سجل نتيجة التشغيل عند اكتماله فقط، ولا تدعِ نجاحًا قبل ظهور GitHub Actions PASS.**

## قبل التشغيل الحقيقي
1. الناشر ما يزال وحدة برمجية غير مربوطة بمشغّل `onSchedule`. تفعيل Scheduler حقيقي يتطلب مراجعة سياسة التأخير وإعادة المحاولة والمراقبة والأعطال.
2. يحتاج تطبيق المستخدم إصدارًا يقرأ `deda_daily_published_task_slots` ويعتمد فقط إعدادًا ساريًا لليوم، دون تغيير الإنجازات القديمة أو أحداث الخريطة.
3. يحتاج مكافآت تلقائية من خادم موثوق بدفتر عمليات ذرية لكل (مستخدم، بطاقة، يوم، إصدار)، وفصل كامل لمحافظ المدير العام؛ لا يمكن تمكين `rewardsEnabled` قبل ذلك.
4. زر إلغاء التعديل المجدول واستعادة التعديل بعد النشر يحتاج ربطًا صحيحًا بواجهة الإدارة؛ خدمة المعاينة متوفرة في المرحلة الثانية فقط.
5. تُفحص قواعد Firebase مقابل آخر إصدار منشور ويجرى اختبار رجوع قبل أي تحديث إنتاجي.

## أولوية السلامة
الوضع الحالي مرحلة تقوية البنية وليس APK جاهزة. يُمنع نشر القواعد/الوظائف/إعدادات المكافآت أو دمج الفرع في `main` قبل اكتمال اختبارات المستخدم والمدير.
