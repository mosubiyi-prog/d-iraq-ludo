# DEDA — Point 1: Google login on a replacement phone with the SAME original UID
Date: 2026-11-14. Isolated source and security QA; no production rollout.

## Scope (owner-approved point 1 only)
An owner who has already linked Google to the proven original DEDA Firebase UID should select "لدي حساب سابق" on a replacement phone and authenticate through that Google provider, without creating a different Firebase owner UID. This task does not restore currencies, level, friends, league or other domain state (points 2 and 3). The app's current Google Settings card remains in its approved position at the top of Settings, above Session Diagnostics.

## Implementation completed on the isolated branch
- **Backend** `functions/deda_google_existing_uid_token_exchange_PRIVATE_NOT_EXPORTED.js`: verifies signed Google RS256 JWT via Google's trusted JWKS, issuer, expected production Web OAuth audience, age, email verification and immutable subject. `getUserByProviderUid("google.com", subject)` must resolve a PRE-EXISTING enabled Firebase Auth principal; canonical `users/UID`, `deda_account_directory/account`, `deda_credentials/account`, `deda_share_ids/originalId`, `deda_sessions/UID`, and any existing social projection must agree, with admin UID rejected. Re-checks the Google provider immediately before issuing a Firebase custom token for THAT verified UID only. AppCheck-authenticated callable, 5-per-hour server-side transaction limit, generic failure responses; no PIN, Google JWT, payment, UID transfer, client-supplied account UID, FirebaseAuth.createUser or owner-profile write.
- **Private, deliberately unexported deployment binding** `functions/deda_google_existing_uid_callable_wiring_PRIVATE_NOT_EXPORTED.js`: requires reviewed production project, approved production OAuth audience and owner-specific release approval before exposing a callable. Neither this module nor its endpoint is imported/exported by `functions/index.js` or deployed.
- **Replacement phone Flutter** `lib/deda_step2_google_replacement_login_100439.dart`: keeps a non-creating Identity Toolkit `autoCreate:false` lookup, requires a server-signed token whose originalUid equals the independently returned Firebase UID, activates actual Play Integrity AppCheck in release mode and checks the attestation, transitions Firebase Auth via `signInWithCustomToken` rather than create-capable `signInWithCredential`, then re-reads server owner/user/original-ID/route/session/linked provider in the original Auth session lane. No local profile/wallet claims. Google was already reachable under the existing "لدي حساب سابق" UI when its explicit private flag is enabled, but it remains disabled in ordinary builds.
- **Tests** `functions/test/deda_google_existing_uid_token_exchange_PRIVATE.test.js`: signed JWT, audience, tamper, expiry, unlinked Google, foreign/changed UID, conflicting directory/credential/route/profile/session/social, admin principal, missing source, provider-unlink race, AppCheck, rate-limit, config approval. Flutter private tests cover ticket matching and prior verified original UID proof. Existing original-phone Google link tests remain intact.

## Real blockers: point 1 NOT YET END-TO-END COMPLETE
1. **Server endpoint is NOT deployed**. The production Functions export `dedaGoogleExistingUidTokenV1` and approved OAuth audience cannot be enabled without a separate actual production configuration/deployment and security review; no production data/Play mutation was authorized for this isolated task.
2. **Play Integrity/AppCheck release trust** for the actual Google Play signing certificate/package has not been confirmed on a real signed install. Private sideloaded release APKs can legitimately fail AppCheck. Never replace this with a production debug-token bypass.
3. **Two-device real owner test** using a separately consented healthy linked original UID and backed-up data is missing. A production Firebase backend must independently prove no alternate principal and the client must confirm provider presence after custom-token SDK sign-in.
4. **Firebase custom-token caveat**: although only a preexisting verified original UID is ever selected server-side (no alternative UID), the SDK can re-create an Auth record with the SAME UID if it is deleted in a narrow race after the server check. The postlogin original Google-provider + Firestore route checks will reject that case; it is *not* an atomic no-Auth-creation primitive. Avoid claiming absolute zero creation without additional server controls.
5. Financial/progress hydration remains explicitly separate. No signed APK containing this functionality is designated a finished DEDA restoration update. No A/B/C conflicted identity or protected production source was modified.

Next action *within point 1*: verify the latest Flutter assembly, then require explicit backend/AppCheck production authorization and live healthy-account two-phone proof before enabling the flag and issuing an APK. DO NOT convert these holds into green claims.
