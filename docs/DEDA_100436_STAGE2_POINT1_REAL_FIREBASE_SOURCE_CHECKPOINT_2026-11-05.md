**الفرع:** `deda-100436-stage2-recovery-buildable-integration-qa-2026-11-05`  
**القاعدة المحمية:** `fea54d7db2e8a24a74267f04a14c9572bcb408ee` — لم تتغير.

## المنجز في المصدر
- وظيفة `dedaVerifyExistingOwnerPin` تقبل تشغيل المحاكي السابق، أو إعداد خادمي مشروط لتفعيل الإنتاج المحدد بالمشروع.
- وظيفتا `dedaIssueLinkedOriginalUidDeviceGrant` و`dedaRecoveryJournalComplete` تستخدمان نفس بوابة إعداد المشروع الحقيقية، وتبقيان مغلقتين افتراضياً.
- جميع مسارات التفعيل الحقيقية تتطلب نفس project ID، موافقة صريحة من المالك في إعدادات الخادم، تأكيد قواعد Firestore، ونجاح فحص UID على الأجهزة. ويُفعّل كل endpoint على حدة.
- ملف `qa/stage2/deda_stage2_auth_guardian_firestore_SOURCE_REVIEW_ONLY.rules` هو **معاينة مراجعة قواعد الجلسة والحارس** المعتمدة بالمحاكي؛ ليس هو ملف Firebase المنتج ولا يغير `firestore.rules`.
- تمنع قواعد الجلسة مستخدم Auth-password من استعارة قواعد PIN القديمة الخاصة بالجلسة المجهولة، وتشترط منحة الجهاز قصيرة العمر، UID الأصلي، عدم وجود صلاحية مدير، وعدم السماح للمستخدم بصناعة منحة أو إيصال توثيق.
- فحص GitHub Actions يقارن معاينة الصلاحيات حرفياً مع الصلاحيات التي يختبرها محاكي Firebase الحقيقي.

## شرط إغلاق رقم 1 فعلياً
1. اختبار الصلاحيات في محاكي Firestore/Auth/Functions، مع منع محاولات UID غريب، إلغاء App Check، حارس المدير، وتعطيل المنح المالية.
2. اختبار تماثل المراجعة مع ملف الصلاحيات الآمن، وفحوص Node/Flutter.
3. **عملية مستقلة لم تحصل هنا:** فحص المشروع الحقيقي والهواتف، اعتماد إعدادات الخادم، نشر وظائف Firebase وقواعد Firestore المراجعة وفق صلاحية Firebase على المشروع نفسه، ثم إعادة قراءة الخادم والتحقق.
4. عدم ربط APK أو نشر تطبيق أو تغيير قواعد الإنتاج بمجرد نجاح الاختبار المحلي. لا تعلن تفعيل Firebase الحي قبل نجاح الخطوة 3.

**الحالة:** مصدر تمهيدي محدّد للاعتماد، **غير مفعل على Firebase الإنتاجي**. لا إضافات خارج نقطة الدخول والحارس والصلاحيات، ولا تعديل للمراجع الأصلية أو الخزان.
