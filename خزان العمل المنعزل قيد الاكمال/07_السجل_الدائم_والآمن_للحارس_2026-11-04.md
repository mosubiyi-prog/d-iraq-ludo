# DEDA — النقطة رقم 1: تجهيز السجل الدائم والآمن للحارس المركزي

**التاريخ:** 2026-11-04  
**المرجع الملزم:** `00_فكشن فكرة 💭أساس العمل 💪👷💪.md`، وحارس الـ12 في `deda_step2_recovery_guardian.dart`.  
**بيئة العمل:** داخل `خزان العمل المنعزل قيد الاكمال` حصراً، من دون تغيير تطبيق 100436 أو قواعد Firebase أو Cloud Functions المنشورة.  
**مصدر التطوير عند الدمج مستقبلاً:** النسخة الناجحة التي يعتمدها المالك صراحة، لا نسخ/دمج فرع 100434 بالكامل.  
**الحالة:** كود نقل فعلي + قواعد مرشحة + خدمة تحقق خادمي مرشحة + اختبارات منطقية داخلية؛ **غير موصولة وغير منشورة ولا مختبرة على Firebase Emulator/هواتف**.

## 1. الملفات التي حُفظت

1. `deda_step2_recovery_journal_firestore.dart` — تنفيذ دائم لعقد `DedaVaultRecoveryJournal`، مصدر Flutter/Dart فقط، `DEDA_STEP2_RECOVERY_JOURNAL=false` افتراضياً. يقرأ من `Source.server`، يرفض الكاش والكتابات المعلقة والـUID المختلف؛ يحجز عملية بالـ`runTransaction` و`FieldValue.serverTimestamp()` ولا يكتب `verified` من الهاتف.
2. `deda_recovery_journal_rules_CANDIDATE_NOT_DEPLOYED.rules` — **مقتطف قواعد فقط، غير منشور**. صاحب UID المرتبط والأصلي يقرأ محاولته أو ينشئ حجزاً `reserved` بالهوية الموثقة وحقول مقيدة، `allow update, delete: if false`؛ القراءة العامة `list` مرفوضة؛ مستندات أدلة الخادم `deda_recovery_server_attestations` تمنع قراءة وكتابة جميع العملاء. معالجة مهمة: قراءة مستند غير موجود لا تستطيع اعتماد `resource.data`، ولذلك رخصة `get` تتحقق من UID/الدليل/الملف/الآيدي الخادميين دون استعمال `resource.data` الغائب.
3. `deda_recovery_journal_completion_CANDIDATE_NOT_EXPORTED.js` — مرشح Firebase Cloud Function (Node 20)، **غير مستورد أو مُصدَّر من `functions/index.js`**. مغلق بخيار `DEDA_RECOVERY_JOURNAL_SERVER_ENABLED` الافتراضي غير مفعّل، ويشترط App Check عند الربط. يتحقق من UID/مزود الدخول/`deda_account_directory`/`users`/`deda_share_ids`/`deda_sessions`، ثم في Transaction واحدة يطابق العملية المحجوزة **بدليل خادم مُنشأ من عامل مصرح** ويكتب `verified` بقراءة لاحقة للعميل. ولا ينفذ شراء أو جوائز أو إعادة رمز.
4. `deda_recovery_journal_server_completion.test.cjs` — **9 اختبارات منطقية بمحوّل Firebase مزيف**: نجحت 9/9 داخل بيئة JavaScript مع توفير بدائل للموصلات؛ ليست `node --test` الحقيقي ولا Emulator. تشمل رفض دليل مفقود أو مختلف وUID آخر ورمز مجهول والتكرار، وسماح الانتقال مرة واحدة فقط عند دليل خادمي صالح. يجب إعادة تشغيلها ببيئة Node 20 واعتماديات `functions/package.json` لاحقاً.

## 2. نموذج التخزين المقترح

المسار:
`deda_recovery_journals/{originalUid}/steps/{intentId}_{codeName}`

مستند الحجز الأولي `reserved` لا يقبل التغيير من العميل:
- `ownerUid`, `accountKey`, `originalId`, `intentId`, `code`, `operationKey`
- `state = reserved`
- `createdAt = request.time / serverTimestamp`

بعد إثبات خادمي مستقل **فقط**:
- `state = verified`
- `receiptId` (مقيد بطول وصيغة)
- `verifiedAt = serverTimestamp`

دليل الخادم المنفصل **غير قابل للقراءة أو الإنشاء من الهاتف**:
`deda_recovery_server_attestations/{originalUid}/receipts/{intentId}_{codeName}`

لا يمكن إنجاز مرحلة `verified` حالياً؛ **لم يُنفّذ بعد كاتب الدليل الخادمي الذي يتحقق من مصدر كل كود**. وبذلك لا يمكن للتطبيق اختلاق نجاح من جواب محلي أو كلمة `completed` مكتوبة من العميل.

## 3. حدود التنسيق مع الحارس والأكواد الـ12

- السجل **واحد** لخدمة الحارس، وليس Journal مستقل لكل واحد من الـ12؛ الحارس يحتفظ بجدول الأكواد والأدوار.
- لا يعمل عند فتح التطبيق أو إنجاز مهمة، ولا يدير FirebaseAuth أو حساب المدير العام.
- هاتفان يستخدمان **نفس originalUid وintentId** يواجهان نفس وثيقة العملية؛ معاملة ذرية تُعيد `true` للإنشاء الجديد فقط و`false` إذا كان الحجز موجوداً. لا يجري الحارس تنفيذ حجز سابق أعاد `false`؛ وإنما يطلب تحقق المصدر.
- انقطاع الشبكة أو انتهاء المهلة بعد إرسال الحجز قد يترك عملية محجوزة على الخادم؛ **لا نعطي تلقائياً إذناً بإعادة التنفيذ**، بل نستأنف القراءة والإثبات.
- **مهم جداً:** تغيير `intentId` ينشئ وثيقة مختلفة. هذا السجل **لا يحل وحده** منع تكرار المكافآت أو استرجاع مجالات حساسة عبر عمليات متعاقبة: قبل تفعيل أي Adapter يكتب بيانات يجب تزويده بمفتاح idempotency **من المصدر الخادمي نفسه** (`sourceRevision` ثابت ومتحقق) وسجل مجال مستقل يسمح بمراجعة التقدم الأحدث في الهاتف الثالث. لا نُسوّق هذا كمنع شامل للتكرار حتى تنجح تلك الشروط.
- `originalPhoneBeforeLink` يستخدم UID مجهولاً قبل الربط؛ **القواعد المرشحة الحالية تحظر هذا الطور** لأنها تتطلب مزوّد Firebase `password`. يجب إعداد إثبات خاص للهاتف الأصلي قبل ربط UID دون تخفيض الأمان. يُمنع فتحه بسماح anonymous عام.
- انتهاء العمل بـ`verified` لا يعني اكتمال الاسترجاع الكامل: المستوى، الرصيد، الإطارات، الآيدي، الهدايا، الدوري، الأصدقاء، الأماكن والأسئلة مجالات تحتاج أدلة منفصلة. `DedaVaultRecoveryResult.fullAccountRestored` يظل `false` في نموذج الحارس.
- لا تعني كتابة سجل الحجز وجود صلاحيات Firebase منشورة؛ `firestore.rules` الحالي لم يُعدّل. أي محاولة تشغيل ببيئة الإنتاج الحالية ينبغي أن **تفشل بأمان**.

## 4. الاختبارات والفحوص: الصادق والمعطل

**منجز:** فحص المصدر وكود النقل، تحقق ثابت من فلاغ الإيقاف والمسارات والحقول، 9 اختبارات منطقية مع محاكاة JavaScript لحالات وظيفة الإنهاء نجحت 9/9، ووجود الحارس وتوصيف 12/12.

**غير منجز، ويمنع التفعيل:**
1. Flutter Analyze / Dart test وتشغيل `deda_step2_recovery_guardian_test.dart` (11 حالة مكتوبة سابقاً) + فحوص السجل الجديد.
2. Firebase Rules Emulator: إنشاء الحجز ورفض تجاوز المستخدم الآخر، خطأ رقم الحساب، عدم وجود Session، منع تحديث `verified` مباشرة، منع `list`/حذف/الوصول إلى أدلة الخادم، وسلوك قراءة مستند غير موجود.
3. Firebase Functions Emulator مع App Check: رفض دليل كاذب أو مسار قديم، انقطاع الشبكة، Transaction retry وكتابة الدليل من مصدر موثوق فقط.
4. كتابة **server-only attestation worker** لكل مجال مع تحقق حقيقي من المصدر وعقد `sourceRevision`، وإثبات عدم تكرار أي عمليات مالية/جوائز عبر intentId مختلف.
5. الحماية من PIN ضعيف/تخمين كلمة السر، إعداد سياسات abuse/rate limits واختبار الهاتف الثاني والثالث ونسخة Play 100340.
6. معالجة قواعد `deda_sessions` الأصلية على هاتف جديد قبل افتراض نجاح قراءة/كتابة الـJournal.
7. عدم تفعيل Journal على الهاتف الأصلي قبل ربط UID حتى تُصمم صلاحيات آمنة خاصة به.

## 5. نقطة توقف رسمية

**الحارس المركزي:** مصمم ومصدره محفوظ؛ غير موصول بالأكواد الحقيقية.  
**السجل الدائم:** مصدر Firestore معاملات ذرية محفوظ؛ قواعد ومرشح التحقق الخادمي محفوظة **غير منشورة**.  
**الاختبارات:** 9 فحوص منطقية ناجحة بمحاكاة؛ ليس تأكيداً لنجاح Firebase أو Flutter.  
**النسخة الأصلية:** 100436 و`lib` وقواعد Firebase لم تتغير؛ الأكواد الـ12 المرجعية محفوظة دون تعديل، ولم ينشأ فرع تطبيق أو APK.

**المسار القادم داخل رقم 1:** فحص قواعد السجل مع قواعد الجلسة الحالية عبر Emulator في فرع فحص مستقل معتمد، ثم اعتماد كاتب أدلة خادم لكل Adapter، وبعدها فقط السماح بربط سجل الحارس على نسخة التطوير الناجحة الجديدة.
